# 从需求到可以验证的产品

适用于用户只有一个想法，或想为已有产品增加能力。先读现有项目、用户提供的资料和已经确认的决定；只补问影响当前实现的未知项。只讨论方案时保持只读；开发请求则在信息足够后持续推进。

## 需求记录

用项目已有任务文件记录以下内容；没有合适位置时使用 `PRODUCT.md`。保持简短，随着实际决定更新，不要求用户填写整张表。

| 记录 | 需要确定的事实 |
|---|---|
| 使用者与任务 | 谁在什么情况下使用，最后完成什么动作 |
| 输入与数据 | 用户输入、已有接口、文件或设备来源；未知数据不编造 |
| 输出与动作 | 页面、文件、结构化结果或业务写入；哪些动作需确认 |
| 平台与使用范围 | 网页、桌面、手机或命令行；本机单人还是服务多用户 |
| 已有资源 | 项目技术栈、登录、业务 API、平台应用、可用开发环境 |
| 第一条完整流程 | 可观察的输入 → 业务处理 → AI/工具 → 结果；使用什么证明完成 |
| 后续改进 | 当前不需要实现的功能、已知假设、待补配置与下一步 |

技术水平不明时直接用业务语言解释选择，例如“需要读取电脑里的文件，可以用桌面应用；先在浏览器使用，可从网页开始”。用户明确选手机时，保留手机目标；可以先做好后端，但不能把后端当手机应用交付。

## 把产品功能与 Agent 工作分开

界面、数据校验、身份授权、统计计算和可靠写入由普通业务代码完成。Agent 用于理解任务、选择工具和生成需要推理的结果。先列出用户实际操作，再选 Agent 能力，避免所有需求都变成一个聊天框。

工具连接真实业务函数，绑定宿主已验证的身份。模型返回“已保存”不代表写入成功；确认工具回执或数据库状态后再呈现结果。根据任务需要接流式进度、取消、会话与恢复，不为一次本机任务预建集群或多租户系统。

## 健身助手示例

用户提出：“我想做一个智能健身助手，每天根据我的情况提供健康及健身建议，分析我的身体状况，提出更长久的健身意见。”

先明确在哪里使用，以及用户准备记录什么。不要默认接入穿戴设备、读取医疗记录或要求填写所有健康信息。可选择的首条流程为：填写自愿提供的目标和今天的情况 → 保存日记录 → 生成供用户参考的运动安排 → 查看历史记录与变化依据。

实现可能包含记录表单、历史列表、建议展示和修改/删除。长期分析必须来自实际保存的记录；记录不足就说明不足。开发阶段采用明确标注的合成数据，不伪造真实身体指标；产品区分一般生活/运动建议与医疗诊断，需要专业判断的问题给合适求助入口，不生成未经依据的诊疗结论。

这只是设计示例。原型不自动接入定时推送、支付、穿戴设备或公共发布；根据用户要求继续补齐。

## 不同领域与已有项目

资料助手需要资料来源、检索依据和可追溯结果；订单助手需要授权订单 API 与用户资源隔离。不能只更换反馈工作台标题，保留与需求无关的数据和工具。

已有项目先定位页面入口、身份和业务 API，复用已有实现；不替换项目登录、框架和数据库。先记录原行为，再接入一条 AI 流程并检查兼容。用户已改的文件先读取与合并，不用整目录模板覆盖。

完成当前需求后留下可启动入口与验证结果。用户继续说“再加每周回顾”时，读取同一需求记录和项目代码，核对历史数据并增量实现，不重新生成另一份互不相连的工程。
