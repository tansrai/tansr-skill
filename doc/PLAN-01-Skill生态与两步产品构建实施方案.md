## 1 目标与产品路径

### 1.1 当前阶段的用户体验

1. 用户从官网复制安装指令，交给自己熟悉的编程助手执行；熟悉终端的用户也可直接运行 npx 命令。安装过程检查环境、安装 Skill、检查发现与加载状态，给出下一步。
2. 用户向同一个助手描述产品需求。助手借助 Tansr Skill 理解目标、选择实现方式、开发应用、接通 Tansr、验证并交付，再按用户反馈持续改进。

“两步”描述用户开始构建产品的入口。账号配置、必要的业务澄清和部署选择在过程中由助手有序引导，不把它们隐瞒成无需任何准备，也不让用户自行研究底层接线。

典型输入：“我想做一个智能健身助手，每天根据我的情况提供健康及健身建议，分析我的身体状况，提出更长久的健身意见。”

这项需求应形成能录入情况、查看建议、记录与回看进展的实际应用。具体功能由需求澄清确定，不预设必须采集某项身体数据，不把通用聊天页面当作完整交付。

### 1.2 品牌与长期方向

- 核心价值：面向每个人，帮助用户把想法做成自己的AI产品；当前首页第一层已包含无开发经验者，通过已有智能助手与Tansr Skill开始构建。入门开发者、成熟技术与产品人员、组织与企业分别获得更深入的开发、集成与持续发展引导，不将普通用户推迟到未来才覆盖。
- 两种起点：从想法新建产品，为已有产品接入 AI。
- 中立定位：连接智能体能力与真实应用，支持不同模型来源，做智能体与人类之间的桥梁，联通世界、服务全球。
- 当前开发辅助 Skill 运行在用户的编程助手中；SDK、Harness 与 Serve 承载所开发产品运行时的能力；应用运行时 Skill 是另一种扩展机制。
- 后续自有助手阶段的路径为“描述想要的产品 → 选择运行平台”。本轮为其保留可复用需求记录、基础工程与验证结果，不开发自有编程助手或新增综合平台。

## 3 架构决策与首批范围

### 3.1 一个入口与按需加载的能力集

用户统一接触“Tansr Skill”。首版采用一个主 Skill 加职责清晰的参考、基础工程和确定性工具；按需求加载。只有出现独立触发与独立维护的实际需要时，才拆成额外 Skill，安装入口不随内部拆分增加。

主入口保留目标、关键分工和任务路由。详细知识按需求理解、新建/接入、运行形态、验证交付、排错维护组织。现有参考可继续使用，不因目录规划而全部重写。保持正常自动发现与显式调用；不强迫无关开发任务接入 Tansr。

确定性动作适合脚本化：环境检查、基础工程生成、配置完整性检查、启动与健康检查。需求理解、业务设计和技术取舍保留给助手，不写死成大量固定问卷。

### 3.2 产品交付的共同骨架

从完整 Web 纵向流程建立基线，复用已有 SDK/Serve 与客户端能力，再适配桌面、移动端。首版不为每个平台重新创建全新模板；优先将已有、可公开分发且验证过的 Demo 整理成可复用起步资产。根据需求组合界面、身份、数据、业务工具、会话、媒体、权限与发布；单用户本机工具不强制引入多租户服务。

新项目使用经过验证的正式发行依赖；基础工程锁文件保证可复现。已有项目沿用锁文件与技术栈，兼容升级另行说明。模板中出现的新 API 必须能在所用发行包的类型或代码中证实，不能靠名称猜测。

平台接入为已有 Tansr 应用用户提供完整可运行路径，不要求另购供应商密钥。自有供应商模式作为用户可选路径。缺少凭据时提供明确标记的离线验证；真实模式失败不得自动换成模拟回答。

每次交付区分：代码生成、本地可用、实际 Tansr 调用通过、可发布构建、实际发布。用户要 Web/App 就交付对应界面与业务流程，不能改成交付 CLI 片段。

### 3.3 首批支持目标

| 维度 | 首批目标 | 对外标注规则 |
|---|---|---|
| 编程助手 | 优先 Codex、WorkBuddy，安装适配接口支持后续扩展 | 分别核实官方机制、实际发现与加载；不因目录相似就声明通用兼容 |
| 安装宿主系统 | Windows、macOS、Linux | 在支持矩阵记录助手与操作系统的有效组合，不把原生缺席的平台组合写为已支持 |
| 产品形态 | Node/CLI、Web、Electron、Android、iOS、原生鸿蒙 | 覆盖现有正式发布能力；每种声称支持的形态都有构建与关键流程证据 |
| 开发任务 | 新建产品、已有项目接入、持续修改和排错 | 三类都必须验证，不能只验证固定演示 |
| 模型与媒体 | 按实际模型目录、授权和 profile 选择 | 不假定每个模型都支持工具、图片或语音，不绕过计费与权限机制 |
| 语言 | 中文为主，安装文案和首页同时准备英文 | 命令、版本和支持状态保持一致 |

上述为首批完整实现目标。S1-01 把资料、环境和发行可用性填入矩阵；发现不可用项保留为原阶段剩余项并说明影响。未经用户明确调整范围，不删除断言或缩小矩阵来勾选完成。

为使已验证能力能够先供用户使用，设置首个可发行基线 R0，属于原阶段交付安排，不另计卡：完整 Web 产品流程与 Node 运行核心必须可用；S1-01 至 S1-04、S1-06、S1-07 完成；A1-01 至 A1-05、A1-07、A1-08 通过；A1-06 中 Web/Node 的适用断言通过。另为这个精确候选保存 S1-08 要求的来源、行为与回归证据。没有这些证据就不能发行 R0。

R0 可进入安装发行与首页闭环，支持列表只包含已验证范围；未完成的原生平台和桌面能力仍在 S1-05、S1-08、A1-06 保留未勾选，E1/A1 不记完整关闭。后续平台验证通过后更新安装包和支持矩阵，不另建任务卡。首页若先上线 R0，只宣传已验证的能力，未通过的平台不能标成已支持。这样可先服务用户，同时保持完整交付统计真实。

### 3.4 安装与内容分发

- 安装器、技能内容、模板清单与兼容基线放在同一受版本管理的来源中，首版随一个 npm 包发布，减少运行时任意下载。根入口名称由 npm 命名空间核实后冻结。
- 仅讨论形态的示意命令为 `npx <已发布的官方包>@latest install`，这不是可执行的发布指令。正式首页只能使用实际发布、验证过的命令。
- 安装适配器处理宿主发现、目录与加载机制；共享逻辑处理清单、文件校验、冲突、原子更新、回退与卸载。优先尊重当前项目约定和用户选择，不向所有检测出的助手自动写入。
- 支持项目级与用户级安装，默认范围依据宿主机制与项目环境决定；交互界面明确显示将写入的位置。无交互时目标不明确则报告可操作选择，不挂起猜测。
- 安装记录至少包含包版本、技能版本、模板基线、目标宿主、安装范围、受管理路径及内容哈希。安装器只能修改自己管理的内容。
- 用户修改文件、未知同名目录、软链接/junction、路径穿越、进程中断、并发安装都要明确处理；不以删除整个目录解决冲突。
- 安装器不存储 appkey、模型密钥或用户业务数据，不给所有工具放权，不改不相关助手设置。必要的账号与凭据配置在开发任务中由安全入口完成。

### 3.5 首页面向当前两步路径

首屏层级为“可得到的产品价值 → 两步操作摘要 → 明确入口”。2026-10-08四层方案建议：首屏主按钮“开始做我的产品”进入同页可直接链接的`#start`引导；引导内主要操作为“复制给智能助手”，次要操作为“查看安装命令”。按钮排布在S3-03本地预览收敛，不把两步安装说明隐藏成只可打开的弹窗。有经验的开发者保留SDK、原快速集成登录和文档入口。产品示例来自本方案实际做出的成果，不包装为客户实绩。

从首屏到安装完成，再到需求输入的文本必须一致。复制成功只说明剪贴板操作成功，不能宣称安装或开发已经完成；无法跨应用确认状态时，清楚引导用户回到编程助手继续。

延续现有品牌、深浅主题和可配置背景体系，重新设计首屏及必要引导区；保持登录入口、资费、Demo 下载、支持入口、备案与英文站等现有功能的有效性。本轮不顺便重写账户、收费体系或公司官网。

## 4 执行方法与勾选规则

- 固定 3 张工程父卡 E1/E2/E3、3 张对抗验收父卡 A1/A2/A3。以下 24 个执行点和 24 个对抗断言属于父卡内部清单，不另拆计进度的小卡。
- `[ ]` 表示未完成，包括部分完成或待验证；`[x]` 仅在该行完成条件全部满足并附有证据时使用。方案编写和检查已有内容不等于工程实现完成。
- 每次继续工作从“下一执行点”开始，先核对最近源码与证据，完成一项更新一项。独立准备可以并行，涉及同一文件与状态的修改顺序执行。
- 每项完成后在执行记录写日期、改动/提交、命令或操作、结果、证据路径和遗留问题；不只写“已完成”。失败保留原记录，修复后追加复验结果。
- 工程父卡关闭要求其执行点全部完成、对应对抗父卡通过、阶段交付物齐全。功能代码、发布、生产上线分别陈述。
- 同一冻结候选集中执行全量检查；无新变更或未解决失败时不重复跑完整测试。跨阶段发现的问题登记在所属原卡，不无限增卡。
- 一般实现选择由执行者依目标自主决定；只有影响产品范围或需要尚未取得的外部操作授权时才提出具体问题，不能反复确认已有决定。
